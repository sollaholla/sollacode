# Web Push

`packages/contracts/src/webPush.ts` defines browser subscriptions, per-installation preferences, and four authenticated RPCs: status, subscribe, unsubscribe, and test. The shared client runtime exposes the RPC commands; the web client presents them under Settings → Agents. Native mobile and Electron continue using their existing notification paths. This implementation does not add native push tokens or change provider adapters.

`WebPushReactor` bridges provider-neutral orchestration activities (`approval.*` and `user-input.*`, including tool action approval prompts) and `VmAgentWorkspace.subscribeAttention`. It recovers recent pending requests and unread agent alerts from projections at startup. Providers that emit those activities are supported without adapter-specific delivery logic.

`WebPush` persists endpoint subscriptions tied to the authenticated session and a deduplicated delivery outbox in migration 78. Registration requires both agent and thread read access. Each endpoint/event key is unique. Subscription age excludes pre-opt-in history; categories and private-by-default payloads are applied before enqueueing. Preference changes settle pending deliveries, and unsubscribe removes them through the foreign key. Request resolutions cancel pending request deliveries.

A scoped drainable worker performs bounded delivery using `web-push`, with a 30-second retry wake, exponential backoff, at most eight attempts, a one-hour vendor TTL, and 24-hour outbox retention. HTTP 404/410 removes expired endpoints; temporary failures retry. Active session, expiry, revocation, and scopes are checked before each batch. Endpoint URLs are limited to supported HTTPS vendor push services, and provider response bodies/endpoints are excluded from logs and client errors. A stable VAPID key pair is created lazily through `ServerSecretStore`; the private key is never sent to a client. The test action reports acceptance rather than claiming on-device delivery.

The outbox is best effort and can deliver twice if the process stops after the vendor accepts a push but before the receipt is persisted. Stable notification tags let the browser replace an existing notification for the same event. Already-accepted notifications cannot be recalled by resolving a request or disabling push.

Agent calls add three kinds next to `agent` and `request`: `call`, `call-ended` and `missed-call`, all gated by the `requests` preference. When an agent rings the person (see [Agent call](../reference/encyclopedia.md#agent-call)), the server publishes a `call` message with tag `call:<callId>` and `path` = `agentCallRoutePath(environmentId, callId)` (`/call/<environment>/<call>`). With `includeDetails` it reads "<agent> is calling" with the call's topic as the body; without, the private text replaces the title too ("Incoming call", "One of your agents is calling."). Its vendor TTL is the seconds left until the ring expires rather than one hour, so a device that reconnects after the ring never shows it. When the call leaves `ringing`, its pending deliveries are cancelled and a replacement with the same tag is published: `missed-call` ("Missed call from <agent>", privately "Missed call") opening the agent's workspace when nobody answered, otherwise a short-lived `call-ended` notice ("Answered on <device>", "Call ended") so the sticky ringing notification leaves every device. The worker shows `call` with `requireInteraction: true`, `renotify: true`, and a ring-pattern `vibrate`, and shows `call-ended` with `silent: true`. Closing a `call-ended` notice a few seconds later is best effort: `event.waitUntil` covers only showing it (a push that ends with nothing on screen is penalised), so a browser that suspends the worker before the timer fires leaves the quiet notice up. Each notification keeps `data: { url, kind?, expiresAt? }` from its push. An open web client also closes notifications tagged `call:<callId>` (`getNotifications({ tag })`) once it sees that call stop ringing, skipping a `missed-call` notice so it stays. A ring stranded by a host restart (no replacement push ever comes) is cleared by the next push: before showing it, the worker closes shown `call` notifications whose `expiresAt` has passed. The call page, not the notification, starts voice: browsers need the Answer tap before the microphone and audio can start.

The root-scoped `web-push-worker.js` displays push messages and constrains notification destinations to the current origin. A tap focuses an existing app window and posts it `{ type: "solla-navigate", url }`, which the app routes in place (a `client.navigate` would reload the page and drop a live call); with no app window it opens one. Same-origin windows under `/api/`, `/oauth` or `/.well-known` show files the server serves, not the app, so a tap skips them. It has **no fetch handler or app-shell cache**, so adding it does not pin clients to old bundles. The manifest enables Home Screen standalone mode. Permission is requested synchronously from a user tap; no permission is requested on page load. Browser subscriptions are replaced if the host's public key changes.

Push is per origin and primary host, not aggregated across all saved environments. Vendor delivery requires outbound internet; a private HTTPS Tailscale origin is sufficient and does not need inbound public exposure. Actual device delivery and OS permission behavior require on-device verification; transport, worker, DOM, and integration tests do not establish that acceptance layer.
