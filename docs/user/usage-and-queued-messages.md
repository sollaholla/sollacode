# Queued messages and usage pacing

Queued delivery waits only for background work that is genuinely in flight. A task whose completion never arrives — an app update or restart mid-task, a provider process that dies, a stall watchdog reaping a CLI — stops holding the queue after its grace window, and one announced by an earlier process never holds it at all. Before this, such a task counted as running forever and queued messages sat unsent against a completely idle thread.

Sending while background tasks run captures the message, images, model choice, and attached context, clears the composer, and shows a queued chip. You can queue multiple messages. The queue starts collapsed; click its header to show or hide the messages. Its count, waiting reason, and failures remain visible, and each thread remembers your choice. Each belongs to its original environment and thread, even when you switch chats. Delivery waits for background work and usage holds to clear. Messages release individually in order, each with its own attachments. When a provider turn is still running, queued input can join that turn after the background tasks finish; an automatic resume does not require waiting for the entire turn to end. New messages queued during that send wait for the next safe opportunity. When the provider has no channel to accept input mid-turn (Deep Code's one-shot `--exec`), Solla stops the running turn so the queued message is delivered as the next turn promptly instead of waiting out the whole turn; a handoff or model change still closes the session, but this restart keeps it so the next turn resumes the same provider session. A rejected send stays available to retry, edit, or cancel. Editing adds the captured content to your current draft without replacing newer text.

Queued messages and image attachments are saved by the server before the composer clears. They survive client and server restarts. Connected web/desktop clients see the same queue; messages from different clients release in server order. Editing restores text and images to the local draft; removing a queued message is shared with other clients. A message already being delivered cannot be removed. Removing a queued message does not block Agent mode from continuing the current task. Stop parks unsent messages for manual sending and stops automatic work.

**Send now** on a queued message stops whatever the thread is currently doing and delivers that message as the next turn, instead of waiting for the running turn or the usage hold to clear. It is a single server-side action rather than a stop followed by a send: pressing Stop cancels every undelivered queued message on that thread, so doing the two by hand would destroy the message you were trying to push through. Send now also revives a message an earlier Stop parked, and one whose scheduler row has already aged out, so anything still visible in the queue panel can be sent. Sending several at once stops the thread once and then delivers them in order — a second Send now never interrupts the turn the first one just started.

The usage guard paces all threads on a provider instance against one account budget. It reserves the next model call, then charges all observed consumption across running threads. Finishing a sibling thread does not erase the cooldown, and lowering reasoning does not grant assumed savings. The first usage report after restart also supplies a spending-rate estimate from elapsed time in the quota window.

Long turns automatically yield after spending their allowance when the runtime returns to model work. Tools, native child-agent work, compaction, and pending human questions are allowed to reach a safe boundary. The server persists the yield before requesting an interrupt and creates one durable resume when budget returns. Closing the client does not discard that server-owned work. Stop, settling the thread, or a newer user turn cancels or supersedes it. Because provider usage arrives after consumption and native calls cannot be split arbitrarily, pacing is an estimate with reserved headroom, not a guarantee that a single unusually expensive call can never reach the provider limit.

Provider settings include a cooldown curve with Linear, Smooth bump, and Late ramp presets. The default allows a pace 10% above the budget immediately after reset. That allowance gradually falls to zero as actual usage reaches 100%. Adjust the early allowance and tightening strength to change the curve. This relaxes pacing, not the provider's hard limit or the reserve for a turn already running.

When the included Codex quota fills and paid usage is allowed, the guard uses the reported credit balance. Known model rates convert input, cached input, and output tokens to estimated credits. The remaining credit balance on the configured dollar scale determines the cooldown. Lower balances produce longer waits; a top-up can release held work. Paid credits are not treated as subscription percentage points or API dollars. Missing balances or unknown model rates do not imply unlimited usage. Unlimited credit accounts are recognized only when the provider reports them explicitly.

Codex credit rates are sourced from the [official rate card](https://learn.chatgpt.com/docs/pricing#token-rates), verified September 6, 2026. Before observing a model's token usage, estimates use 150,000 uncached input tokens and 15,000 output tokens per call. Astra fast mode uses the documented 2.5× credit multiplier. These are estimates; provider balance reports remain authoritative. Claude, Grok, and Antigravity use their reported usage windows. Antigravity meters Gemini separately from Claude and GPT. Cursor and OpenCode have no account-budget enforcement when their adapter supplies no usage windows. The cooldown curve is enforced on the server for all clients; the curve editor and shared queue panel are available in web and desktop clients, including the web client on a phone. Paused scheduler work remains Working in thread and agent lists. Cooldown chips show an estimated resume countdown and progress; when that estimate expires they say the budget is being rechecked. Resume now overrides the hold. Resume message chips reveal their full text on click or tap. At narrow widths, Resume now sits below the text and spans the card width. Long countdowns use days, hours, and minutes. Automatic pacing lets each resumed turn work for at least two minutes before yielding again at a safe boundary.

The chapter/turn navigation rail is capped at 240 pixels and also fits shorter viewports. More turns reduce marker spacing instead of making the rail taller. Keyboard navigation still reaches every turn.

Paid Codex optimization uses a remaining-balance scale, defaulting to $0–$50, with no time window or midnight reset. The dollar display uses an editable estimate of 25 credits per USD (1,250 credits at $50); set the conversion to your purchase price. A balance above the scale is treated as full. The selected curve increases pacing and lowers permitted effort as the balance declines. The scale is an optimization reference, not a cumulative spending cap or an automatic credit purchase. Included subscription quotas still follow their provider reset windows. Accepted queued messages release the composer immediately, even while the provider remains paused.

Expand the cooldown chip by clicking or tapping its text to adjust **Thinking effort**. The slider offers only levels supported by the selected model. Estimated wait and time saved appear immediately above it and update as you slide. **Apply** saves the choice for queued work and rechecks the budget; **Resume now** also saves any un-applied slider selection before overriding the pause.

Effort estimates start with conservative relative call costs: Low 80%, Medium 90%, High 100%, Extra High 110%, Max 120%, and Ultra levels 130%. These are starting assumptions, not provider pricing guarantees. Three observed calls for the same model, effort, and service tier replace that level’s default. These estimates can vary with task size and other active agents. Lower effort does not erase credits or quota already spent, so sometimes it saves no wait time. The measurements survive server restarts and the estimates travel with the shared pause notice to connected web and desktop clients.

A completed agent sign-off retires automatic continuation before the usage guard can put it into cooldown. Explicit queued user messages remain deliverable. Expanded command text collapses on a tap or click; selecting text and using embedded controls does not collapse it.

The expanded chip compares other supported models at the selected effort where available. Each quote names its limiting usage window and shows Ready now or an estimated wait. Non-Fable families bypass the Fable-specific window, but still obey shared account limits. Applying another model saves that model and effort for queued work and rechecks admission. These alternative quotes use the normal service tier. Savings appear in green with an upward arrow; a longer wait appears as negative savings in red with a downward arrow.

Remote desktop touch input gives a second finger 250 milliseconds to begin a pinch before sending a held press to the host. A quick single-finger tap still clicks on release; a second finger during that interval cancels the pending click. Mouse input remains immediate.
