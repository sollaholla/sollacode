# Queued messages

Queued delivery waits only for background work that is genuinely in flight. A task whose completion never arrives — an app update or restart mid-task, a provider process that dies, a stall watchdog reaping a CLI — stops holding the queue after its grace window, and one announced by an earlier process never holds it at all. Before this, such a task counted as running forever and queued messages sat unsent against a completely idle thread.

Sending while background tasks run captures the message, images, model choice, and attached context, clears the composer, and shows a queued-messages chip at the top right of the composer, beside the side-chat and connection chips. You can queue multiple messages. The chip shows how many are waiting and turns red when one failed; select it to see the messages, why they are waiting, and **Send now**, **Edit**, and **Cancel** for each. **Edit** closes the popup, since the message moves into the composer. Each belongs to its original environment and thread, even when you switch chats. Delivery waits for background work and usage holds to clear. Messages release individually in order, each with its own attachments. When a provider turn is still running, queued input can join that turn after the background tasks finish; an automatic resume does not require waiting for the entire turn to end. New messages queued during that send wait for the next safe opportunity. When the provider has no channel to accept input mid-turn (Deep Code's one-shot `--exec`), Solla stops the running turn so the queued message is delivered as the next turn promptly instead of waiting out the whole turn; a handoff or model change still closes the session, but this restart keeps it so the next turn resumes the same provider session. A rejected send stays available to retry, edit, or cancel. Editing adds the captured content to your current draft without replacing newer text.

Queued messages and image attachments are saved by the server before the composer clears. They survive client and server restarts. Connected web/desktop clients see the same queue; messages from different clients release in server order. Editing restores text and images to the local draft; removing a queued message is shared with other clients. A message already being delivered cannot be removed. Removing a queued message does not block Agent mode from continuing the current task. Stop parks unsent messages for manual sending and stops automatic work.

**Send now** on a queued message stops whatever the thread is currently doing and releases the queue, instead of waiting for the running turn or the usage hold to clear. Earlier queued messages keep their order, so one of them can reach the provider before the message whose button you pressed. It is a single server-side action rather than a stop followed by a send: pressing Stop cancels every undelivered queued message on that thread, so doing the two by hand would destroy the message you were trying to push through. Send now also revives a message an earlier Stop parked, and one whose scheduler row has already aged out, so anything still listed under the queued-messages chip can be sent. Presses made before the first message reaches the provider form one group: the thread stops once and those messages remain queued for delivery in order. After the provider accepts any queued message, a later Send now can interrupt again, even if that earlier message was not one whose button you pressed. A delayed click on a message already delivered does nothing and does not block sending the remaining messages.

Claude sometimes keeps working between your prompts, such as when a background task it started reports back. A message sent then is delivered as your own next turn, which ends that stretch of work, rather than being steered into it. Before 0.1.712 such a message could not join it and retried every second without end, showing **Sending…** and **Waiting to retry**, and **Send now** could not get it through. If a provider still reports a turn as running after it has ended, queued delivery now waits 15 seconds between attempts instead of one, and the server log notes `thread-work.active-turn.ended-turn-still-listed`.

A message you send to Claude while it is working joins that turn as soon as Claude takes it in. Before 0.1.727 one such message could get stuck in a way only a restart cleared: if the session stopped at the wrong moment (**Send now** or **Stop** pressed right after sending, say), it waited forever for Claude to take it in. Every later message in that thread then read **Queued for Claude** until the running turn ended, for hours across many turns. Now a message caught that way goes back to the queue and is delivered as the next turn. A message that is not taken in mid-turn is still delivered as the next turn, as before. Messages sent while a turn could not start are carried into the next one; those are now marked delivered once that turn starts, so later turns no longer send the same text again (one "resume" had reached Claude four times). Before 0.1.728, very long threads (hundreds of thousands of work-log rows) could freeze the whole app for 13 to 47 seconds at a time. That happened while restarting a session, when background tasks were marked stopped, while refreshing a thread's waiting-for-you count, and once at every launch. During a freeze nothing moved: **Send now** and **Stop** looked dead, Claude looked unresponsive, and a Stop that gave up waiting could close the session under a message that was just being sent. Those lookups now read only the rows they need.

The chapter/turn navigation rail is capped at 240 pixels and also fits shorter viewports. More turns reduce marker spacing instead of making the rail taller. Keyboard navigation still reaches every turn.

Remote desktop touch input gives a second finger 250 milliseconds to begin a pinch before sending a held press to the host. A quick single-finger tap still clicks on release; a second finger during that interval cancels the pending click. Mouse input remains immediate.
